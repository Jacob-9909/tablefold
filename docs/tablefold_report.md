# tablefold 결과 보고

## 1. 문제

현재 t2sql-package는 질문 하나에 SQL 하나를 만들기까지 테이블 선택, 컬럼 선택, 관계 파악, SQL 생성을 각각 LLM 호출과 벡터 검색으로 처리한다. 단계가 많고 단계마다 스키마 정보가 프롬프트에 쌓인다.

여기서 세 가지가 발생한다. 정보가 많아 LLM이 핵심 테이블을 놓친다. 조인 경로를 매번 다시 추론하면서 같은 질문에 다른 조인이 나온다. 호출이 누적되어 응답이 늦다.

질문 시점에 정보를 고르는 대신, 미리 접어두면 이 세 가지가 같이 줄어들 것이라고 봤다. 이것이 tablefold의 출발점이다.

## 2. 탐구 - Wren AI

같은 문제를 다루는 오픈소스로 Wren AI를 봤다. 두 개의 축으로 해결한다.

첫째는 MDL(Modeling Definition Language)이다. 물리 스키마 위에 의미 계층을 사람이 YAML로 작성한다. `orders`와 `customers`의 카디널리티, `총매출`의 산출 공식, `is_refunded` 같은 계산 필드를 선언한다. LLM은 이 의미 계층을 향해 SQL을 쓰고, Rust 엔진이 CTE 확장과 JOIN 주입으로 물리 SQL을 되돌린다. 조인이 확률적 추론에서 결정론적 변환으로 넘어가는 지점이 여기다.

둘째는 질의 시점 압축이다. MDL이 잘 정리되어도 모델이 수백 개면 프롬프트에 안 들어간다. 그래서 스키마를 테이블/컬럼/지표 단위로 쪼개 벡터 DB에 색인하고, 질문마다 Top-K를 뽑아 LLM 2차 검증으로 2~3개만 남긴다. 쿼리당 토큰이 80~90% 줄어든다.

여기서 가져온 것은 "조인을 LLM에게 맡기지 않는다"는 발상이다. 가져오지 않은 것은 MDL 작성과 질의 시점 RAG다. 둘 다 운영 비용이 크다.

## 3. 설계 - tablefold

물리 스키마를 소수의 넓은 논리 모델로 접고(Fold), 그 모델을 향해 쓰인 논리 SQL을 실행 가능한 물리 SQL로 되돌린다(Expand). 사람이 쓰는 MDL을 그래프 알고리즘이 대신 만든다.

접는 쪽은 다섯 단계다.

| 단계 | 하는 일 |
|---|---|
| 테이블 조회 | DDL 또는 카탈로그에서 테이블·컬럼·PK·FK·행 수 수집 |
| 관계 복구 | 선언되지 않은 FK를 이름 패턴과 PK 매칭으로 추론하고, 실제 데이터 위반율로 검증 |
| 앵커 선택 | 모델의 중심을 정한다. 탐욕적 집합 커버로 최소 모델 수에 최대 테이블 커버 |
| 비용 판별 | 흡수 시 늘어나는 필드 수를 계산. 레이어 예산과 모델별 상한을 따로 둬 한 앵커가 독식하지 못하게 한다 |
| 모델 합성 | N:1은 컬럼을 그대로 인라인, 1:N은 GROUP BY로 선집계 후 조인 |

되돌리는 쪽이 여섯 번째 단계다. LLM이 쓴 논리 SQL을 AST로 파싱해, 실제로 쓰인 필드에 필요한 조인만 생성하고(조인 프루닝) 필터를 집계 서브쿼리 안으로 밀어넣는다.

관계 복구를 데이터로 검증하는 부분이 실측에서 효과가 컸다. 21개 모델·450개 필드 규모의 스키마에서 선언된 FK는 7개였고, 데이터 위반율 검증으로 45개를 추가 복구했다.

## 4. 원리와 트레이드오프

핵심 원리는 두 개다.

**1:N을 인라인하지 않는다.** 주문 1건에 결제 3건이 붙은 테이블을 그대로 조인하면 주문 금액이 3배로 집계된다. 그래서 역방향은 반드시 선집계한 뒤 조인한다. 이 규칙이 없으면 압축한 모델의 합계가 조용히 틀린다.

**앵커가 답할 수 있는 질문을 정한다.** 이것은 설계상의 선택으로 보였지만 실측하면 성능 지표다. NL2SQL 스타 스키마(19테이블, 165컬럼)에서 앵커 모드만 바꿔 측정했다.

| 앵커 모드 | 논리 모델 | 프롬프트 | 답변 가능 질문 |
|---|---|---|---|
| 팩트 | 10개 | 5,874자 | 27.0% |
| 차원 | 9개 | 16,959자 | 94.4% |
| 혼합 | 19개 | 22,633자 | 100% |

팩트 앵커의 27%는 이론적 수치가 아니다. 골드셋 48문항을 팩트 앵커 레이어만 주고 돌렸을 때 12건이 "매출과 경영계획이 서로 다른 모델에 있어 답할 수 없다"로 거부됐고, 그 12건이 정확히 이 차이다.

즉 압축률과 답변 가능 범위는 서로 반대로 움직인다. 압축률 하나만 보면 테이블을 버려서 좋아지는 지표를 쫓게 된다. 프롬프트가 3.9배 길어지는 대가로 못 묻는 질문이 사라지는 쪽이 NL2SQL에서는 대체로 남는 장사였다.

## 5. Wren AI와의 차이, 그리고 적용 대상

| 구분 | Wren AI | tablefold |
|---|---|---|
| 논리 계층 출처 | 사람이 MDL 작성 | 그래프 알고리즘이 생성 |
| 압축 시점 | 질의 시점(질문마다) | 빌드 시점(스키마마다 1회) |
| 필요 인프라 | 벡터 DB, 임베딩, 재선택 LLM 호출 | 없음 |
| 지표 정의 | MDL에 선언 | 없음 |
| 스키마 규모 | 수백 테이블까지 확장 | 수십 테이블 |

tablefold가 유리한 부분은 질의 시점에 인프라가 없다는 것이다. 레이어는 이미 만들어져 있고 질문은 그것을 그대로 읽는다. 검색이 놓쳐서 답을 못 하는 실패 유형 자체가 존재하지 않는다. 스키마가 바뀌면 다시 돌린다.

Wren AI가 유리한 부분은 규모와 업무 지식이다. 질의 시점에 검색하므로 수백 테이블에서도 동작한다. `총매출`의 정의나 기준 조직 체계처럼 스키마에 적혀 있지 않고 사람만 아는 것은 자동 유도로 채울 수 없다.

적용 대상을 실측으로 판정했다. 현재 운영 중인 DW 마트 스키마(82테이블)는 부적합이다. 전부 이미 비정규화된 뷰이고 FK와 PK가 0개다. 정답 SQL 203개 중 202개가 조인을 쓰지 않는다. 접을 것이 없다. 반면 NL2SQL 스타 스키마(차원 9 + 팩트 10)는 적합하다. 골드셋 89개 중 81개(91%)가 조인을 필요로 하고 20개는 팩트를 둘 이상 참조한다. 여기서는 압축 엔진이 아니라 조인 제거기로 쓰는 것이 맞다.

## 6. 한계와 보완 방향

구현하면서 두 가지에 부딪혔다.

조인 키로 연결되지 않는 테이블을 다룰 수 없었다. 웨어하우스는 FK 선언이 없고 컬럼 명명 관례도 일정하지 않아 자동 추론이 실패한다.

압축 비용 대비 이득을 처음부터 데이터로 재지 못했다. 앵커 모드 실측은 구현이 끝난 뒤에 붙였다. 실제 활용할 데이터와 업무 질문을 충분히 확보하지 않고 구현에 들어간 것이 원인이고, 이번 작업에서 가장 아쉬운 부분이다.

보완 방향으로 네 가지를 설계해뒀다.

- **파생 키.** 값은 다르지만 함수를 씌우면 같아지는 컬럼을 관계로 인식한다. 매출의 `20250801`과 기간의 `202508`은 `LEFT(_, 6)`으로 조인된다. 이번 스키마에서 매출(일별)과 경영계획(월별)의 그레인 불일치가 여기 걸렸다.
- **비등가 조인.** `min_salary`~`max_salary` 구간 테이블처럼 등호가 아닌 조건을 `BETWEEN`으로 매칭한다.
- **UNION.** `F_SALES_2024`와 `F_SALES_2025`처럼 연도로 쪼개진 테이블을 가상 컬럼으로 하나로 합친다.
- **줄 단위 정의.** 한 줄이 무엇을 뜻하는지 키 컬럼으로 명시한다. `(YYYYMMDD, ORG_CD, ITEM_CD)`로 선언하면 어떤 단위로 집계해야 하는지가 결정된다.

업무 지식이 안 들어간다는 점은 자동 유도로는 메울 수 없다. 자동 생성된 레이어를 초기 뼈대로 쓰고 그 위에 사람이 지표 정의와 비즈니스 이름을 얹는 방식이 현실적이다. Wren AI의 MDL 작성 비용 문제와 tablefold의 업무 지식 부재는 서로의 답이다.

프롬프트 크기 상한은 질의 시점 검색을 결합해서 푸는 것이 방향이다. 다만 그 순간 tablefold가 피하려던 벡터 DB 의존이 돌아오므로, 어느 규모부터 그 비용을 지불할지를 먼저 정해야 한다.

## 7. 산출물

파이프라인 결과를 확인하는 웹 데모를 만들었다. 물리 스키마가 몇 개의 논리 모델로 접혔는지, 각 모델이 어떤 테이블을 흡수했는지, 원본 관계 그래프와 압축된 논리 모델 ERD를 나란히 비교할 수 있다. 논리 SQL을 입력하면 물리 SQL로 확장되는 과정과 프루닝된 조인 수가 표시된다. 앵커 모드는 팩트/차원/혼합 세 가지를 전환해 위 표의 수치를 재현할 수 있다.
